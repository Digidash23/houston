# Mobile store release


`.github/workflows/mobile-release.yml` runs on the same published `cloud-v*`
releases as mobile OTA updates and can be dispatched from `main`. The OTA
workflow publishes production only for a `cloud-v*` release whose tagged
release commit was cut from `main` (the daily cut keeps it off `main`, so its
first parent is checked) and whose `main` base is not older than the live
bundle's (the `+<sha>` suffix of the signed manifest's version);
`scripts/ota-commit-guard.sh` enforces both. Legacy `v*` releases publish
nothing. Each platform reports one
named notice and skips when its required credentials are absent. When present,
it builds the production mobile bundle with OTA enabled, syncs Capacitor, and
uploads an iOS archive to App Store Connect or a signed Android App Bundle to
the Play internal track. Store text is in `store/metadata/`; App Review notes
are in `store/review-notes.md`.

## Protected environments (repository admin)

Both workflows read their signing and store credentials from GitHub
environments, so a workflow edited on another branch cannot use them:

1. Create the environments `mobile-updates` and `mobile-release` (Settings →
   Environments). For each, set **Deployment branches and tags** to *Selected*
   and allow the branch `main` and the tag pattern `cloud-v*`.
2. Move `HOUSTON_MOBILE_UPDATE_SIGNING_KEY` from repository secrets into
   `mobile-updates`, then delete the repository secret.
3. Move `ASC_KEY_P8_B64`, `ASC_KEY_ID`, `ASC_ISSUER_ID`,
   `ANDROID_UPLOAD_KEYSTORE_B64`, `ANDROID_UPLOAD_KEYSTORE_PASSWORD`,
   `ANDROID_UPLOAD_KEY_ALIAS`, `ANDROID_UPLOAD_KEY_PASSWORD` and
   `PLAY_SERVICE_ACCOUNT_JSON` into `mobile-release`, then delete the
   repository secrets.
4. A job with an environment presents the OIDC subject
   `repo:gethouston/houston:environment:mobile-updates`. Check the
   `github-deploy-web` Workload Identity binding matches on the repository
   attribute, not on a `ref:`-based subject, before the first run.

Manual dispatches of both workflows run only from `main`.

Create these secrets from the named services (repository secrets unless an
environment is named):

| Secret | Source |
| --- | --- |
| `ASC_KEY_P8_B64`, `ASC_KEY_ID`, `ASC_ISSUER_ID` (environment `mobile-release`) | Base64 private App Store Connect API key and its Key ID and Issuer ID from App Store Connect. |
| `ANDROID_UPLOAD_KEYSTORE_B64`, `ANDROID_UPLOAD_KEYSTORE_PASSWORD`, `ANDROID_UPLOAD_KEY_ALIAS`, `ANDROID_UPLOAD_KEY_PASSWORD` (environment `mobile-release`) | Upload key generated by `scripts/make-upload-keystore.sh`; store its passwords and alias. Keep a separate backup of the keystore. |
| `PLAY_SERVICE_ACCOUNT_JSON` (environment `mobile-release`) | Google Cloud service account JSON with Play Console release access and the Android Publisher API enabled. |
| `HOUSTON_MOBILE_UPDATE_PUBKEY` | Existing OTA signing public key, base64 DER SPKI. |
| `HOSTED_ENGINE_URL`, `FIREBASE_API_KEY`, `FIREBASE_AUTH_DOMAIN`, `FIREBASE_PROJECT_ID`, `POSTHOG_KEY`, `POSTHOG_HOST`, `SENTRY_DSN` | Existing production web/mobile build values. |

Create these repository variables:

| Variable | Source |
| --- | --- |
| `APPLE_TEAM_ID`, `HOUSTON_APPLE_TEAM_ID` | The same Apple Developer Team ID. The first signs iOS; the second builds the web association file. |
| `HOUSTON_ANDROID_CERT_SHA256` | Comma-separated SHA-256 fingerprints of the **Play App Signing** certificates from Play Console for `assetlinks.json`. The local upload certificate is a different key. |
| `FIREBASE_APPLE_SERVICE_ID` | Existing Apple Services ID configured in Firebase Authentication. |
| `HOUSTON_MOBILE_STORE_URL_IOS`, `HOUSTON_MOBILE_STORE_URL_ANDROID` | Store listing URLs. Each platform's store job skips with one named notice when its URL is absent; production OTA builds still publish. |

## Raising the required native build

An OTA publish (and a rollback) never raises the manifest's
`required_native_build`: it carries the channel's live value forward, because a
higher floor locks every older build behind an update screen with nothing to
install while the store builds wait in Play internal testing or App Review.
Once the new store builds are live for everyone on both stores, run
**Mobile OTA updates** manually from `main` with action
`raise-required-native-build`, the channel, and the new floor (at most the
lowest live store build number). It re-signs the channel's current bundle with
the higher floor; it refuses a value at or below the current one.

The committed `native-compat.json`, Xcode `CURRENT_PROJECT_VERSION`, and Gradle
`versionCode` remain the native compatibility floor (currently 4): OTA bundles
skip builds below `min_native_build`, and store uploads must be at least
`required_native_build`. Store jobs
override the upload build number with `github.run_number * 100 +
github.run_attempt`, after checking it is at least `required_native_build`.
The run number rises across workflow runs and the attempt rises on reruns;
attempts must stay below 100. The store version (Xcode `MARKETING_VERSION`,
Gradle `versionName`) is the release tag without `cloud-v` (`cloud-v1.0.7`
uploads `1.0.7`); a `main` dispatch uses the highest `cloud-v*` tag by version, so once that
version is approved, cut a new release instead of dispatching. The committed
`1.0` is only the local-build default. Advance all three committed values together for
a native capability change. Play requires a first app bundle uploaded through
its Console before the API upload can create subsequent releases.

The web production and staging builds generate `/.well-known` association files
when `HOUSTON_APPLE_TEAM_ID` and `HOUSTON_ANDROID_CERT_SHA256` are set. Only `/` opens in the
native app; plan links stay on the web because the store app cannot sell plans. Firebase Hosting serves both files
as JSON at `app.gethouston.ai`; absent values omit the respective file with a
named build log. The iOS privacy manifest declares the app's collected data;
Capacitor 8 ships its own privacy manifest. The app manifest includes the
UserDefaults reason required by the installed Capgo updater; the app target's
Swift code calls no required-reason API directly.
